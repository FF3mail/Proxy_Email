Файлы, необходимые для реализации

mail-proxy-daemon.py — основной файл, обе затронутые функции:

_stream_file_via_smtp() — где именно происходит цикл RCPT и вызов DATA (нужно добавить счётчик принятых и условный rset()+return False);
send_via_external_smtp() — вызывающая функция, чтобы проверить, как именно она обрабатывает False от _stream_file_via_smtp() и подтвердить, что путь "файл остаётся в очереди" действительно идентичен пути отказа MAIL FROM/DATA (это критично для правильной оценки пункта 1 выше).


schema.sql — не требуется для этого исправления напрямую, но полезно иметь под рукой для контекста таблицы clients/external_accounts, если потребуется понять, откуда берётся список recipients.
DELTA-transit_anchor.md — для проверки, не описано ли где-то ожидаемое поведение при частичном отказе RCPT (например, есть ли требование уведомлять администратора об отклонённых адресах отдельно от факта неотправки письма целиком).


Проведи локальное исправление дефекта.

Контекст:

В функции _stream_file_via_smtp() (mail-proxy-daemon.py) выполняется цикл RCPT TO
по списку recipients.

Сейчас при отказе конкретного RCPT (код ответа не в (250, 251)) выполняется
только logger.warning — обработка цикла продолжается.

После завершения цикла команда DATA вызывается всегда, независимо от того,
сколько (если хоть один) получателей было фактически принято сервером.

Из-за этого возможна ситуация, когда DATA выполняется и письмо считается
успешно отправленным (return True), хотя ни один получатель не был принят —
письмо физически никому не доставляется, при этом файл вложения после этого
удаляется демоном как успешно обработанный (молчаливая потеря данных).

ЖЁСТКИЕ ОГРАНИЧЕНИЯ:

1. НЕ менять архитектуру проекта.
2. НЕ выполнять рефакторинг SMTP-подсистемы.
3. НЕ менять сигнатуры функций.
4. НЕ добавлять новые классы.
5. НЕ менять структуру очередей.
6. НЕ менять бизнес-логику кроме исправления дефекта.
7. НЕ создавать новые файлы.
8. НЕ добавлять зависимости.
9. НЕ переносить код между модулями.
10. Если требуется архитектурное изменение — остановиться.

Шаг 0 (обязателен перед патчем, не является частью исправления):

Прежде чем вносить изменения, изучи, как вызывающий код (send_via_external_smtp()
и далее по цепочке — воркер SmtpWorkerPool, _scan_existing_outgoing(),
_reserve_outgoing_file()/_release_outgoing_file()) обрабатывает возврат False
из _stream_file_via_smtp() при уже существующих сценариях отказа (отказ
MAIL FROM, отказ DATA). Подтверди и укажи в ответе явно: приводит ли
существующий return False к тому, что файл письма НЕ удаляется и будет повторно
подобран при следующем цикле _scan_existing_outgoing(), либо к какому-либо
другому документированному поведению. Новое исправление должно использовать
ровно тот же путь обработки ошибки — без создания альтернативной логики
"сохранения в очереди".

Требуемое поведение:

- Вести учёт успешно принятых RCPT (счётчик или список, накапливаемый в цикле
  по фактическим кодам ответа 250/251).
- Если после завершения цикла количество принятых RCPT равно 0:
  - DATA не выполнять.
  - Если команда MAIL FROM уже была отправлена и принята (что выполняется перед
    циклом RCPT в текущем коде) — обязательно вызвать server.rset() перед
    return, чтобы явно завершить незаконченную SMTP-транзакцию и не оставить
    соединение в неопределённом состоянии для следующей команды.
  - Залогировать отдельным сообщением уровня ERROR факт прерывания отправки
    из-за нулевого количества принятых получателей (с указанием адресов,
    которые были отклонены, и кодов ответа сервера) — это сообщение
    дополняет, а не заменяет существующие logger.warning по каждому отказу.
  - Вернуть False — ровно то же значение и тот же тип, что уже возвращается
    функцией при отказе MAIL FROM или DATA. Не использовать исключение и не
    менять тип возвращаемого значения.
- Если принят хотя бы один RCPT (счётчик >= 1):
  - Выполнять DATA как сейчас, без изменений в этой ветке.
  - Существующие logger.warning по каждому отдельно отклонённому получателю
    сохраняются без изменений — частичный отказ (например, 2 из 3 получателей
    принято) не должен прерывать отправку принятым получателям.

Формат ответа:

1. Причина дефекта.
2. Минимальный patch.
3. Возможные побочные эффекты.
4. Регрессионные тесты.
