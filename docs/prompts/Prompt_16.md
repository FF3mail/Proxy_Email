Проведи локальное исправление дефекта.

Контекст:

В проекте существует настройка:

imap_encryption

Допустимые значения (ENUM на уровне схемы БД, см. schema.sql):

- ssl
- tls
- none

Сейчас функция poll_external_imap() в mail-proxy-daemon.py всегда использует
IMAP4_SSL независимо от значения imap_encryption — поле читается из БД, но не
используется при установке соединения.

Требуется исправить дефект.

ЖЁСТКИЕ ОГРАНИЧЕНИЯ:

1. НЕ менять архитектуру проекта.
2. НЕ выполнять рефакторинг.
3. НЕ переименовывать функции.
4. НЕ менять структуру БД.
5. НЕ менять сигнатуры функций.
6. НЕ создавать новые модули.
7. НЕ добавлять внешние зависимости. Использование модуля ssl из стандартной
   библиотеки Python (для STARTTLS) допустимо и не считается новой зависимостью.
8. НЕ переносить логику между файлами.
9. НЕ изменять бизнес-логику кроме исправления дефекта.
10. Если исправление требует архитектурных изменений — остановиться и объяснить почему.

Требуемое поведение:

- ssl  → использовать IMAP4_SSL (текущее поведение, без изменений)
- tls  → использовать IMAP4 + явный вызов starttls() с
         ssl.create_default_context() (стандартная проверка сертификата должна
         остаться включённой — не отключать verify_mode/check_hostname)
- none → использовать IMAP4 без шифрования

Во всех трёх ветках обязательно сохранить timeout=IMAP_TIMEOUT при создании
соединения (конструкторы IMAP4 и IMAP4_SSL поддерживают этот параметр) — сейчас
он защищает воркер от зависания, и его потеря в новых ветках является
регрессией, а не допустимым побочным эффектом.

Обработка неизвестных или отсутствующих (NULL/пустая строка) значений
imap_encryption:

- НЕ делать silent fallback на ssl или любой другой режим по умолчанию.
- Залогировать ошибку уровня ERROR с указанием account.email и фактического
  значения поля.
- Прервать обработку этого аккаунта (return из функции), не предпринимая
  попытки установить соединение.
- Это намеренное решение: на уровне схемы БД поле защищено ENUM, поэтому
  недопустимое значение в норме недостижимо штатным путём (через веб-панель);
  если оно всё же встретилось — это сигнал о проблеме (прямая правка БД,
  несогласованная миграция), который не должен маскироваться попыткой угадать
  режим подключения.

Дополнительно:

- Сохранить существующее логирование (формат и уровень сообщений об успешном/
  неуспешном подключении, аутентификации и т.д. — не менять без необходимости).
- Обратная совместимость: все существующие аккаунты с уже сохранённым в БД
  значением imap_encryption='ssl' должны продолжать подключаться ровно так же,
  как до исправления (через IMAP4_SSL), без какой-либо разницы в поведении.
