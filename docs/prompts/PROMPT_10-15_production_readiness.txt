PROMPT 10
Устранение разрыва dot-stuffing на границах чанков при потоковой SMTP-передаче
Проект: DELTA-transit (mail-proxy)
Файл: mail-proxy-daemon.py
Затронутые функции: _stream_file_via_smtp() (доставка в локальный SMTP) и
send_via_external_smtp() (отправка через внешний SMTP).
Проблема:
Экранирование начальной точки строки (dot-stuffing, RFC 5321) выполняется
независимо для каждого чанка вызовом chunk.replace(b'\n.', b'\n..'). Если
последовательность "\n." оказывается разорвана границей чанка (конец одного
чанка — "\n", начало следующего — "."), экранирование не срабатывает. Внешний
SMTP-сервер интерпретирует одиночную точку в начале строки как конец команды
DATA, и письмо обрывается до достижения реального конца сообщения. При
вложениях 100-150 МБ (порядка 2000-2400 чанков по 64 КБ на письмо) вероятность
такого совпадения границы не равна нулю и накапливается со временем при
большом потоке писем.
Требования:
1. Гарантировать корректное экранирование "\n." независимо от того, на какой
   стороне границы чанков оно оказалось. Допустимые подходы: переносить последний
   байт предыдущего чанка в начало проверки следующего перед применением replace;
   либо обрабатывать поток как непрерывную последовательность строк, сохраняя
   "хвост" неполной строки между вызовами записи/отправки.
2. Сохранить потоковую передачу — НЕ читать файл целиком в память ни в одной
   из функций.
3. Сохранить текущий размер чанка (64 КБ, см. константу CHUNK_SIZE) и текущий
   механизм передачи через sock.sendall().
4. Исправление должно быть применено идентично в обеих функциях.
5. Не менять остальную бизнес-логику: формирование заголовков письма, работу
   с MAIL FROM/RCPT TO, обработку ошибок SMTP-диалога, очереди, воркеры, OAuth2.
Запрещено (общие ограничения проекта, действуют всегда):
- менять архитектуру пула воркеров (ImapWorkerPool/SmtpWorkerPool, максимум
  20 IMAP + 20 SMTP воркеров);
- заменять пул соединений MariaDB (mysql.connector.pooling.MySQLConnectionPool)
  одиночными подключениями;
- удалять или ослаблять поддержку OAuth2 (XOAUTH2);
- возвращаться к модели "1 референт = 1 поток";
- ослаблять systemd hardening (mail-proxy.service);
- предоставлять пользователю www-data доступ к Maildir или группе vmail;
- нарушать совместимость формата шифрования между PHP Cryptor и Python Cryptor
  (AES-256-GCM с обратным чтением legacy AES-CBC, общий префикс "gcm:");
- доверять заголовкам X-Real-IP/X-Forwarded-For без проверки REMOTE_ADDR.
Результат:
- unified diff patch, затрагивающий только указанные функции (не весь файл);
- объяснение изменений (5-8 предложений);
- словесное описание тест-сценария, подтверждающего, что разрыв "\n." на стыке
  чанков теперь корректно экранируется.

PROMPT 10.2

Устранение рассинхронизации реестра watchdog при первоначальной регистрации референтов

Проект: DELTA-transit (mail-proxy)

Файл: mail-proxy-daemon.py

Затронутые функции:

start()
_setup_watchdog_for_referent()
Проблема

При запуске демона выполняется первоначальная регистрация watchdog для уже существующих активных референтов:

for ref in referents:
    self._setup_watchdog_for_referent(ref)

Однако после успешной регистрации наблюдателя идентификатор референта не добавляется в множество:

self._watched_referent_ids

Позднее _sync_database_state() сравнивает текущее состояние БД с содержимым этого множества и может ошибочно считать уже зарегистрированные референты новыми, что приводит к повторным вызовам _setup_watchdog_for_referent() и дублирующим операциям регистрации наблюдателей.

Требования
После успешной регистрации watchdog обеспечить синхронное обновление:
_watched_referent_ids;
_referent_path_registry (как сейчас).
Не допускать появления расхождения между фактически зарегистрированными watchdog и содержимым _watched_referent_ids.
Не менять алгоритм работы _sync_database_state().
Не менять архитектуру watchdog.
Не менять логику мониторинга Maildir.
Не менять многопоточную архитектуру проекта.
Сохранить существующие блокировки (threading.Lock) и правила потокобезопасности.
Результат

Предоставить:

diff -u, затрагивающий только необходимые строки;
краткое объяснение изменений (3–6 предложений);
описание сценария проверки, подтверждающего отсутствие повторной регистрации watchdog после старта демона.

PROMPT 10.3

Исследование корректности обработки RCPT TO перед переходом к SMTP DATA

Проект: DELTA-transit (mail-proxy)

Файл: mail-proxy-daemon.py

Затронутые функции:

_stream_file_via_smtp()
send_via_external_smtp()
Предпосылка

В SMTP-сессии выполняется последовательность:

MAIL FROM
RCPT TO
RCPT TO
...
DATA

Необходимо проверить, существует ли ситуация, при которой все команды RCPT TO были отклонены сервером, однако код всё равно продолжает SMTP-диалог и отправляет команду DATA.

Согласно RFC 5321 сервер может отклонять переход к DATA при отсутствии хотя бы одного успешно принятого получателя.

Задача исследования

Провести анализ реализации и определить:

Может ли в текущем коде возникнуть переход к DATA при нуле принятых получателей.
Как обрабатываются ответы SMTP на команды RCPT TO.
Есть ли проверка факта наличия хотя бы одного успешного RCPT TO.
Какие SMTP-серверы (Postfix, Exim, Exchange, Microsoft 365, Gmail SMTP и др.) наиболее чувствительны к такому сценарию.
Может ли проблема приводить к:
лишнему сетевому трафику;
ошибкам доставки;
неверному учёту статуса отправки;
ложным повторным попыткам доставки.
Соответствует ли текущее поведение RFC 5321.
Ограничения

Исследование должно быть только аналитическим.

Запрещено:

вносить изменения в код;
предлагать патч без подтверждения наличия проблемы;
менять SMTP-архитектуру проекта;
изменять бизнес-логику доставки.
Результат

Предоставить:

вывод о наличии или отсутствии проблемы;
ссылки на соответствующие требования RFC 5321;
оценку риска (низкий / средний / высокий);
при подтверждении проблемы — отдельное предложение на исправление в формате нового задания (без самого патча).

PROMPT 11
Устранение зависания исходящих писем при временной недоступности внешнего ящика
Проект: DELTA-transit (mail-proxy)
Файл: mail-proxy-daemon.py
Затронутые компоненты: MaildirHandler (обработчик watchdog для Maildir/new),
ProxyDaemon._sync_database_state(), ProxyDaemon._scan_existing_outgoing().
Проблема:
Если файл появляется в Maildir/new референта в момент, когда у референта нет
ни одного активного external_account (например, идёт смена учётных данных в
веб-панели), обработчик on_created логирует предупреждение о том, что файл
"будет подхвачен при следующем сканировании", но фактической повторной
проверки backlog для уже отслеживаемых референтов не существует — повторное
сканирование (_scan_existing_outgoing) вызывается только при старте демона и
при переходе референта из неактивного в активный список наблюдения. Тот же
комментарий о "следующем сканировании" присутствует и в обработке переполнения
SMTP-очереди (SMTP_QUEUE_MAXSIZE). В обоих случаях файл может оставаться
необработанным неограниченно долго, до перезапуска демона.
Требования:
1. Обеспечить, чтобы файлы в Maildir/new, не поставленные в очередь при первой
   попытке (по причине отсутствия активного аккаунта или переполнения очереди),
   реально повторно проверялись в течение разумного интервала — например, в
   рамках уже существующего цикла _sync_database_state (раз в 60 секунд), для
   всех отслеживаемых референтов, а не только для новых.
2. Исключить повторную постановку в очередь файлов, которые уже успешно
   обработаны или находятся в процессе отправки (избегать дублей).
3. Решение должно быть единым для обеих причин задержки (нет аккаунта /
   переполнена очередь).
4. Не менять формат взаимодействия с watchdog API, не менять структуру Maildir.
Запрещено (общие ограничения проекта, действуют всегда):
- менять архитектуру пула воркеров (ImapWorkerPool/SmtpWorkerPool, максимум
  20 IMAP + 20 SMTP воркеров);
- заменять пул соединений MariaDB одиночными подключениями;
- удалять или ослаблять поддержку OAuth2;
- возвращаться к модели "1 референт = 1 поток";
- ослаблять systemd hardening;
- предоставлять www-data доступ к Maildir/группе vmail;
- нарушать совместимость PHP Cryptor ↔ Python Cryptor;
- доверять X-Real-IP без проверки REMOTE_ADDR.
Результат:
- unified diff patch;
- объяснение (5-8 предложений), описывающее выбранный механизм (периодический
  rescan, retry-список, иной) и почему он минимально ресурсоёмкий при до 500
  одновременно активных референтов.
