# PROMPT-79 — Сводный реестр решений (pre-production roadmap)

Собрано по итогам обсуждения 2026-09-22, до старта реализации.
Не заменяет ADR-001 (журнал прохождения писем), а дополняет его
операционными решениями по PROMPT-79.

## 1. Удаление legacy/shadow

- Legacy и shadow режимы маршрутизации, per-referent overrides и
  `referent_only` watch — изымаются из проекта как несоответствующие
  целям программы. Не документируются, не покрываются тестами, не
  сохраняются как путь отката после релиза (откат — через тег на
  предыдущий master, см. обсуждение выше).
- Пилот остаётся в режимах: relationship_live / relationship_live /
  relationship_only. Поведение для уже совпадающих писем не должно
  измениться — это критерий приёмки удаления.
- Порядок: удаление кода (79.1) — до документации и до тестов людьми.
- Схема БД (nullable-колонки overrides) удаляется отдельной миграцией
  ПОСЛЕ soak-периода (79.4), не одновременно с кодом.

## 2. Утилизация писем без relationship

- Демон окончательно не находит соответствие по relationship →
  запись в журнал прохождения писем (причина `no_relationship`) →
  удаление письма из источника.
- Fail-closed: сбой поиска (БД недоступна, таймаут, исключение) —
  НЕ считается «нет совпадения». Письмо остаётся UNSEEN, повторяется
  при следующем опросе.
- Relationship найден, но деактивирован администратором →
  запись в журнал с причиной `relationship_inactive` → удаление письма
  из источника **тем же действием**, что и при `no_relationship`
  (IMAP STORE `\Deleted`/EXPUNGE или unlink Maildir). Уведомление —
  по общим правилам §4 (молча для inbound-from-internet; notify+delete
  для outbound-from-referent). Код причины отдельный только для triage
  в панели; `event_type` остаётся `disposed`.
- **Поправка 2026-09-23 (PROMPT-79.2, уточнение оператора):** ранее в
  этом пункте было «деактивирован — письмо НЕ удаляется, остаётся
  UNSEEN». Это отменено. Модель продукта: деактивация = временно
  вакантная позиция референта (запись по клиенту переиспользуется и
  позже реактивируется правкой имени), поэтому почта на неактивную
  связь утилизируется, а не копится UNSEEN.
- Запись в журнал должна быть надёжно зафиксирована ДО необратимого
  действия (IMAP STORE \Deleted / EXPUNGE, удаление файла Maildir).
  Если запись не удалась — письмо не удаляется.

## 3. Утилизация писем с невалидным вложением

Единое событие «вложение невалидно» с подпричинами:
- вложений нет (0);
- вложений больше одного (**только исходящие** от референта; см. поправку ниже);
- расширение файла не входит в список разрешённых архивов;
- тема письма не совпадает точно с именем файла вложения, включая
  расширение (**для входящих — только при N=1**; при N≥2 тема родителя
  не проверяется — Subject дочерних писем синтезируется из имени файла).

**Поправка 2026-09-23 (PROMPT-79.2c):** входящее письмо с N≥2 вложениями
больше **не** утилизируется целиком по причине multiple_attachments.
Клиент может легитимно прислать несколько архивов в одном письме.
Демон разделяет (split) каждое вложение с разрешённым расширением в
отдельное локальное письмо (PROMPT-76 fan-out) и доставляет последовательно.
Вложения с запрещённым расширением пропускаются (лог); если после фильтра
не осталось ни одного доставляемого — утилизация источника с
disallowed_extension. Исходящий путь (референт → клиент) **без изменений**:
ровно одно вложение, список расширений, совпадение темы.
Interim-hold PROMPT-79.2-incident-check снят этим промптом.


**Поправка 2026-09-24 (PROMPT-79.2d, ADR заказчика D1–D8):** заменяет правила
79.2c («только архивы», «тема родителя при N≥2 не проверяется») и старые
правила N=1 для входящих из интернета.

- **Один путь** для любого входящего с N≥1 вложений: split/fan-out каждого
  разрешённого по расширению вложения в отдельное локальное письмо.
  Архив **не обязателен**.
- **Разрешённые расширения входящих:** `APPROVED_INBOUND_EXTENSIONS` =
  архивы ∪ изображения (`jpg/jpeg/png/gif/webp/bmp/tif/tiff/heic/avif/ico`).
  **SVG исключён**. Исходящий путь и `APPROVED_ARCHIVE_EXTENSIONS` **без
  изменений** (картинки на исходящих по-прежнему отклоняются).
- **Запрещённые части** не доставляются: журнал `event_type=skipped`,
  `reason=disallowed_extension`. Если после фильтра нечего доставлять —
  dispose источника `disallowed_extension`. N=0 → `zero_attachments`.
- **Лимит** `MAX_INBOUND_ATTACHMENTS=20` (считаются все attachable parts
  до фильтра). 21+ → dispose всего письма `too_many_attachments`
  (без «первых 20»).
- **Тема родителя (D7):** проверяются только имена **архивов** (мультисет),
  порядок безразличен, пробелы в именах — через backtracking
  (`check_inbound_subject`). Изображения в Subject — ошибка. Сообщение
  только из изображений — тема не проверяется (принятый риск).
- **Тема дочернего (D8):** для каждой доставленной части (архив и картинка)
  Subject = имя файла с расширением, регистр сохранён.
- **Доставка at-least-once**; дедупликация не делается.
- **Валидация только по расширению** (без magic bytes) — осознанный риск F6.



**Поправка 2026-09-24 (PROMPT-79.2e):**

- **Inline (E1):** вложением считается только часть с `Content-Disposition`,
  содержащим `attachment`. Inline/cid/без disposition — не вложения: не
  доставляются, не журналируются, не входят в лимит 20 и Subject. Письмо
  только с inline (логотип без документа) → `zero_attachments` (в `detail`
  имена inline при наличии). Картинки с disposition=attachment принимаются;
  те же файлы как inline — блокируются. Риск: клиенты, шлющие PDF/картинки
  только inline без архива-вложения, блокируются намеренно.
- **missing_filename (E3):** attachment без имени → skip + journal
  `missing_filename` (не fail-closed UNSEEN loop). Если все части безымянные
  → dispose `missing_filename`.
- **Seen → journal → delete (E4):** для любого inbound dispose: сначала
  успешный journal INSERT, затем STORE Seen, затем Deleted+EXPUNGE. Сбой
  journal → UNSEEN. Сбой Seen → WARNING, delete всё равно. Сбой delete после
  Seen → WARNING, письмо остаётся Seen (без повторного poll/journal).

**Поправка 2026-09-24 (PROMPT-79.2f):** признак вложения — только
`get_content_disposition() == 'attachment'`, не подстрока в заголовке
(имя файла `attachment.png` при `inline` не считается вложением).

Регистр при сравнении темы письма и расширений вложений — см. Issue
#26 (https://github.com/FF3mail/Proxy_Email/issues/26).

Проверка по расширению файла, без сверки сигнатуры (magic bytes) —
осознанное упрощение для MVP предпродакшна. Проверка на подмену
расширения — кандидат для F6 (доработки по фидбеку тестеров), не
входит в объём PROMPT-79.

Лимит размера вложения — НЕ проверяется демоном (отменено). Размер
ограничивается локальным почтовым сервером его собственными
механизмами отказа в отправке, вне зоны ответственности демона.

Те же условия безопасности, что в п.2: fail-closed при сбое парсинга
MIME (не считать браковкой), запись в журнал раньше необратимого
действия.

## 4. Уведомления при удалении письма

| Источник письма | Причина удаления | Действие |
|---|---|---|
| Из интернета (входящее от клиента) | нет relationship / невалидное вложение | Молча удаляется. Уведомление НЕ отправляется (риск backscatter на внешний адрес). |
| От референта (исходящее из локальной почты) | нет relationship / невалидное вложение | Удаляется + локальное уведомление референту. |

Текст уведомления референту (единый для всех подпричин раздела 3;
без упоминания размера):

```
Тема: Ошибка доставки — <наименование клиента>

Уважаемый(ая) <Референт>,

Ваше письмо для <наименование клиента> от <дата>, отправленное в <время>,
не может быть доставлено в связи с нарушением формата.

Пожалуйста, убедитесь, что:
— к письму приложен ровно один файл — защищённый паролем архив;
— тема письма точно совпадает с названием файла архива, включая
  расширение (например, Contract_2026.zip).

После исправления, пожалуйста, отправьте письмо повторно.

--
Автоматическое уведомление. На это письмо отвечать не нужно.
```

## 5. Журнал прохождения писем (см. ADR-001 для полного обоснования)

- Отдельный поток данных, независимый от debug-лога демона.
- Одна запись на письмо: доставлено или отклонено (с подпричиной).
- Хранение записей журнала: 1 год, отдельная политика ротации/архивации.
- Debug-лог демона: срок хранения — как настроено в системе (без
  изменений в рамках PROMPT-79).
- Панель мониторинга (раздел «Мониторинг») строит из журнала два
  представления:
  1. табличное — прохождение писем, человекочитаемый вид, например:
     «Письмо от `<Референт>` для `<Клиент>` получено на
     `<локальный ящик>` в `<дата время>`, отправлено на
     `<внешний ящик>` в `<дата время>`» (и симметрично для входящих);
  2. отдельное поле — нестандартные события (отклонённые письма) с
     указанием причины и признака «референт уведомлён / не уведомлён».
- Механизм хранения журнала (файл vs БД), точный набор полей и
  правило планового удаления записей старше года — открытые вопросы
  реализации, закрываются в рамках PROMPT-79.2 (см. ADR-001,
  раздел «Последствия»).

## 6. Не входит в объём PROMPT-79 (перенесено)

- P4 (pre-fetch size guard / буферизация письма в ОЗУ при приёме) —
  статус меняется с «open» на «deferred»; ревизия при появлении
  проблем в постпродакшне. Триггер должен быть измеримым (см.
  обсуждение выше: OOM-kill, порог RSS демона, отказ на письме
  определённого размера) — формулировка триггера остаётся задачей
  для отдельной правки anchor, не для PROMPT-79.
- `monitor.php:603` (различение «файл отсутствует» / «нет прав» в
  панели) — отдельный кандидат-промпт.
- V4 (проверка выживания после перезагрузки хоста, PROMPT-78) —
  ближайшее окно обслуживания.
- Проверка на подмену расширения файла (magic bytes) — кандидат F6.
