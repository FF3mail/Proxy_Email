1. Архитектура и файловая структура

DELTA-транзит — корпоративный почтовый прокси-шлюз, передающий файлы между сотрудниками офиса (референтами) и внешними контрагентами через электронную почту. Система состоит из четырёх слоёв:

  • Nginx + PHP-FPM — веб-панель администратора (/var/www/mail-proxy);
  • MariaDB — база данных mail_proxy (референты, аккаунты, OAuth2-токены, провайдеры);
  • iRedMail (Postfix + Dovecot) — почтовый стек, локальная доставка референтам;
  • Python-демон (systemd-служба mail-proxy, пользователь vmail) — мост между Maildir референтов и внешними IMAP/SMTP-серверами контрагентов.

Примечание о статусе файлов репозитория. В корне репозитория присутствуют два установочных скрипта: delta-transit-install.sh (полный установщик, 12 фаз, формирует production-отчёт и проводит финальный аудит) и mail-proxy-setup.sh (более ранний, облегчённый скрипт, который устанавливает только Python-зависимости демона, базовые группы/права и systemd-юнит, без настройки Nginx/PHP/MariaDB и без финального аудита). Оба файла рабочие и непротиворечивы друг другу по правам и группам, но на момент написания документа mail-proxy-setup.sh не используется основным сценарием установки — он оставлен в дистрибутиве как вспомогательный инструмент для ручной пересборки окружения демона (например, при восстановлении после сбоя без полной переустановки веб-панели). Используйте delta-transit-install.sh как основной установщик; обращайтесь к mail-proxy-setup.sh только при сценариях из раздела 10.

2. Установка и первичная настройка

2.1. Предварительные требования

Установщик delta-transit-install.sh ожидает следующие пакеты (устанавливаются автоматически на фазе Packages, если отсутствуют): python3, python3-pip, python3-venv, mariadb-server, nginx, postfix, dovecot-imapd, logrotate, openssl, curl. iRedMail (Postfix/Dovecot) должен быть развёрнут и настроен для доставки почты референтам до запуска установщика — установщик не разворачивает почтовый стек, только интегрируется с ним.

Обязательные файлы дистрибутива, без которых установщик завершится с ошибкой: mail-proxy-daemon.py, mail-proxy.service, logrotate-mail-proxy, schema.sql, requirements.txt. Запускайте установщик из директории, где лежат эти файлы.

2.2. Применение schema.sql

Установщик применяет схему автоматически на фазе Database. Если требуется применить её вручную (например, при восстановлении):

mysql -u root -p < schema.sql

Схема создаёт базу mail_proxy (charset utf8mb4, collation utf8mb4_unicode_ci) и пять таблиц: referents, clients, external_accounts, oauth_tokens, oauth_providers. Поля auth_type, imap_encryption, smtp_encryption в external_accounts защищены на уровне СУБД через ENUM — недопустимые значения СУБД отклонит на уровне INSERT/UPDATE (подробнее — раздел 9, пункт 2). Таблица oauth_providers предзаполняется записями для Google, Yandex и Microsoft с ON DUPLICATE KEY UPDATE, то есть повторное применение schema.sql безопасно обновит эндпоинты провайдеров без создания дублей.

2.3. Запуск delta-transit-install.sh

Установщик выполняется в 12 последовательных фазах:

  1. Preflight — проверка обязательных файлов, прав запуска (root), ОС.
  2. Packages — установка APT-пакетов.
  3. Database — применение schema.sql, создание пользователя БД.
  4. Users/Groups — создание mail-proxy-logs, mail-proxy-crypto, удаление www-data из группы vmail, если он там оказался (см. раздел 8).
  5. Python — создание venv в /opt/delta-transit/venv, установка requirements.txt.
  6. Web — копирование web/ в /var/www/mail-proxy, права 0644 / 0755.
  7. Postfix — интеграция с локальным Postfix.
  8. Dovecot — интеграция с локальным Dovecot.
  9. PHP — настройка php.ini (лимиты, раздел 4); фаза пропускается с предупреждением, если PHP не установлен.
  10. Nginx — установка фрагмента лимита тела запроса (раздел 2.6).
  11. systemd — установка mail-proxy.service, systemd-analyze verify, daemon-reload, enable.
  12. Validation — запуск службы, проверка её активности, наличия лога, входа в БД, отсутствия плейсхолдеров CHANGE_ME / mail-proxy.local в конфигурации.
  13. Production audit — финальная проверка (раздел 2.6) и запись отчёта /root/delta-transit-install-report.txt (права 0600).
sudo ./delta-transit-install.sh

2.4. Настройка /etc/mail-proxy/db.conf и crypto.key

Оба файла создаются установщиком в /etc/mail-proxy/ с правами 0640, владелец root:mail-proxy-crypto. Группа mail-proxy-crypto создаётся установщиком и в неё включаются www-data (для веб-панели) и vmail (для демона) — это единственный легитимный путь чтения секретов обоими процессами без предоставления избыточных прав друг на друга.

db.conf — INI-файл с секцией [db]:

[db]
db_host = 127.0.0.1
db_user = mail_proxy
db_pass = <пароль>
db_name = mail_proxy

crypto.key — файл из ровно 64 шестнадцатеричных символов (256 бит), генерируется установщиком через Python. Из этого hex-ключа оба компонента (Python-демон и PHP-Cryptor) детерминированно выводят реальный 256-битный ключ AES через SHA-256(hex_string). И PHP-, и Python-сторона при чтении crypto.key строго проверяют длину (64 символа) и корректность hex.

2.5. APP_BASE_URL в config.php

web/config.php определяет константу APP_BASE_URL, используемую исключительно для построения redirect_uri в OAuth2-flow (раздел 5). Эта константа не строится из заголовка Host входящего запроса — это намеренное решение безопасности для защиты от Host header injection.

2.6. Пример конфигурации Nginx (allow/deny, X-Real-IP)

Важно: фаза Nginx установщика создаёт только файл /etc/nginx/conf.d/mail-proxy.conf со строкой client_max_body_size 210M; и требует вручную добавить include /etc/nginx/conf.d/mail-proxy.conf; внутрь блока http {}.

server {
    listen 443 ssl;
    server_name mail-proxy.example.local;
    root /var/www/mail-proxy;
    index index.php;
    location / {
        allow 10.0.0.0/8;
        allow 172.16.0.0/12;
        allow 192.168.0.0/16;
        allow 127.0.0.1;
        deny all;
        try_files $uri $uri/ /index.php?$query_string;
    }
    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_param HTTP_X_REAL_IP $remote_addr;
        fastcgi_param HTTP_X_FORWARDED_FOR $proxy_add_x_forwarded_for;
        fastcgi_pass unix:/run/php/php8.1-fpm.sock;
    }
}

4. Настройка лимитов вложений (150 МБ)

Целевой лимит вложения для конечного пользователя — 150 МБ. Фактический лимит на уровне почтовых протоколов и веб-сервера установлен с запасом — ≈200–210 МБ (с учётом Base64 overhead ~33%).

Скрипт configure_limits.sh применяет согласованные значения и перезапускает затронутые службы. Перед изменением конфигурационных файлов создаёт резервные копии с суффиксом .bak_YYYYMMDD_….

sudo ./configure_limits.sh

4.1. Интерактивный шаг: квоты почтовых ящиков (MariaDB)

После настройки max_allowed_packet в конфигурации MariaDB скрипт останавливается и запрашивает данные с клавиатуры. Этот шаг не описан в таблице выше, но обязателен для завершения скрипта: без ответов на запросы configure_limits.sh не продолжит настройку Nginx/PHP-FPM и перезапуск служб.

Запрос 1: пароль root MariaDB

MySQL root password:
  • Ввод скрыт (символы не отображаются на экране).
  • Используется тот же пароль root, который задавался при первоначальной установке MariaDB / iRedMail.
  • Пароль нужен для выполнения SQL-запроса UPDATE vmail.mailbox SET quota = … от имени mysql -u root.

Запрос 2: выбор почтовых ящиков

Email-адреса через запятую или --all-referents:

Допустимы два варианта:

  1. Список адресов через запятую — например: referent1@example.com, referent2@example.com. Скрипт проверяет формат каждого адреса и выполняет UPDATE vmail.mailbox SET quota = 10240 WHERE username IN ('…');
  2. Флаг --all-referents — скрипт задаёт дополнительный запрос: 
    Домен:
    и выполняет UPDATE vmail.mailbox SET quota = 10240 WHERE username LIKE '%@<домен>';, поднимая квоту всем ящикам указанного домена.

Значение квоты

Скрипт устанавливает quota = 10240 в таблице vmail.mailbox (схема iRedMail). В этой колонке значение хранится в мегабайтах (МБ); 10240 соответствует 10 ГБ дисковой квоты на ящик. Это отдельный параметр от лимитов Postfix/Nginx/PHP в таблице выше: он ограничивает суммарный объём хранимой почты в Dovecot/iRedMail, а не размер одного вложения.

После выполнения запроса скрипт выводит строку вида Updated mailbox rows: N, где N — число затронутых строк. Если N = 0, проверьте правильность адресов или домена.

Интерактивный режим — не для автоматизации. У configure_limits.sh нет флагов для передачи пароля MariaDB или списка ящиков неинтерактивно (нет --password, --mailboxes и т.п.). Перенаправление stdin (echo … | ./configure_limits.sh) и запуск из cron/CI не поддерживаются — оператор должен присутствовать у консоли и отвечать на запросы вручную. Для полностью автоматизированного развёртывания этот шаг нужно выполнять отдельно в интерактивной SSH-сессии после основного установщика.

5. Анализ логов

Логи демона пишутся в /var/log/mail-proxy/mail-proxy-daemon.log. Логи веб-панели направляются в /var/log/mail-proxy/web_admin.log.

2025-01-15 14:23:01,123 INFO mail_proxy.daemon: XOAUTH2 AUTH succeeded for account@example.com
[2025-01-15 14:23:01] CSRF token mismatch for action referent_save

6. Мониторинг

Страница monitor.php доступна по адресу https://<APP_BASE_URL>/monitor.php и отображает текущее состояние службы, доступность логов, критические ошибки и статус авторизации OAuth2/IMAP/SMTP.

7. Резервное копирование и восстановление

Критически важные объекты для бэкапа:

  • Ключ шифрования: /etc/mail-proxy/crypto.key (максимальная критичность)
  • Конфигурация БД: /etc/mail-proxy/db.conf
  • Дамп базы данных MariaDB mail_proxy

9. Известные ограничения и эксплуатационные особенности

9.1. Буферизация писем в памяти при приёме через IMAP

Библиотека imaplib возвращает письмо целиком в памяти процесса. При пиковой нагрузке формула расхода RAM: RAM_peak ≈ IMAP_WORKER_COUNT × размер_письма_RFC822 ≈ 20 × 200 МБ ≈ 4 ГБ.

9.3. Разрыв dot-stuffing на границе SMTP-чанков

Статус: закрыт (PROMPT 10). Функция удерживает последний байт каждого чанка в переменной carry для исключения разрывов экранирования на стыках.

10. Типовые неисправности (troubleshooting)

При ошибках старта проверьте валидность hex-ключа: wc -c /etc/mail-proxy/crypto.key (ожидается 64 символа) и права доступа.

11. Обновление системы

Штатный перезапуск службы безопасен в любой момент. Входящие письма остаются в статусе UNSEEN до подтверждения локальной доставки, а исходящие сохраняются в Maildir/new референтов.
